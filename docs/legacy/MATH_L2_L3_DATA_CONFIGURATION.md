# MATH Level 2–3 主线数据配置

更新：2026-10-13。本文确定后续实验的数据范围与预算，不回写已完成训练的历史。具体预算为本项目建议，尚未构建，不是开源项目验证过的最优配方。

## 1. 数据来源与用途

| 阶段 | 来源 | 数量与状态 |
|---|---|---|
| 最初SFT | unsloth/OpenMathReasoning-mini 的题目与生成解答 | 505条训练样本；来源由用户补充确认，原始筛选索引仍需追溯 |
| 后续SFT补充/重建 | MATH官方train中的Level 2–3 | 新实验预留600个不同问题作为SFT候选，最终合格示范不超过600条 |
| GRPO主实验 | 剩余MATH train Level 2–3 | 每题4答筛选；首轮训练池最多1024道，不足则按实际数量使用 |
| 开发验证 | MATH train Level 2–3预留 | 新实验建议200道，按level和subject分层；已训练或调参暴露过的题不能作为全新留出 |
| 主测试 | MATH官方test中的Level 2–3 | 沿用冻结清单；本地历史主评测2024道，官方原始2025道中排除了1道训练重叠题 |
| 可选补充 | GSM8K train | 默认不加入；仅在明确算术/文字建模短板时单独对照 |

主目标是MATH Level 2–3数学推理。训练与测试采用同一等级范围、不同题目实例。原始505条来自外部数据，不称为MATH Level 2–3子集；外部题目也必须参与测试重叠检查。

已有历史GRPO归档包含GSM8K，累计3072题；那是旧的混合训练实验。本文MATH主线不能沿用3072作为已训练题数。用户报告的第三轮SFT结果与数据量、checkpoint的对应关系仍需补齐。

## 2. 开源项目支持什么

- [Unsloth OpenMathReasoning-mini](https://huggingface.co/datasets/unsloth/OpenMathReasoning-mini)：当前展示19252行，包含problem、expected_answer、generated_solution等字段；展示样本的generation_model为DeepSeek-R1。它是外部生成解答来源，不自带MATH Level 2–3标签。505是项目选用量，不是整个数据集大小。
- [SimpleRL-Zoo](https://github.com/hkust-nlp/simpleRL-reason#dataset)：公开区分不同MATH等级组合，并提供GSM8K/MATH数据。这支持按目标与模型能力选择数据范围，不要求本项目固定混入GSM8K。其Medium、Hard等级范围也不同于本项目。
- [Open-R1 pass-rate filtering](https://github.com/huggingface/open-r1/blob/main/scripts/pass_rate_filtering/README.md)：生成回答、计算正确比例后筛选可验证任务。本项目借鉴流程；每题4答、保留1–3答对是本地设置，不冒充上游唯一配方。

生成解答与Base输出分布不同、轨迹较长、局部推导不完整，都是可检查的因素；不能仅凭数据集名称断言它造成了SFT退化。用实际505条检查长度、来源和错误，不把整个上游数据集评价为低质量。

## 3. 先分题，再构建答案

本地MATH train L2原始1348条、L3原始1592条，共2940条；历史规范化去重后2939题。

在可重新划分且没有历史暴露冲突的前提下，预算示例为：

```text
2939道不同MATH训练题
 ├─ 200道开发验证
 ├─ 600道SFT候选（补充实验与Base轨迹重建共用这个分区）
 └─ 最多2139道GRPO筛选候选
```

2139还没扣除外部505题重叠、额外留出、近似重复与题面/判分问题，实际应由清单计算。若继承旧adapter，其训练暴露必须合并计入；本预算不直接适用于在历史训练之后重新划分“未见题”。

按七个subject和L2/L3分层抽题，接近原始训练分布，检查小类是否遗漏；不强制每个学科一样多，不根据测试集错题比例决定训练配额。分层主要依据训练标签与开发验证中的诊断。已用于错误分析的旧测试仍可报告，但不能再称盲测。

600是为小规模格式SFT预留的候选预算，并给GRPO保留约两千题。它不是已经筛出600条正确示范，也不是证明600足够。冻结划分后，不把SFT失败候选随意转入GRPO。

## 4. SFT三轮如何衔接

最初实验使用505条外部示范。已有补充集的1379条是本地修订版本，不能仅凭文件数量判定某次实际训练用了多少条；应按对应训练manifest确认。

新一轮可在预留600道MATH题内比较两种示范：

1. 复核过的官方/外部解答，修复必要推导并统一输出格式。
2. 原始Base每题生成4份解答，最终答案经Math-Verify核验，推导完整性经模型辅助与争议样本复核；每题选一份合格解答，仅统一推导/答案边界及真实EOS。

四份均无合格解答时，保存失败原因并检查知识点缺失；纯自身轨迹实验不混入未经标记的教师解答。不要机械截断长解答。最终数量N必须由筛选记录得到，N≤600，候选回答最多2400份，不能把2400说成训练题数。

为了验证“更适配Base的解答”是否有帮助，应在两种示范都可用的同一批N道题上做对照：同一起点、题目、模板和训练配置，报告长度及监督token差异。这样比直接比较“505外部题”与“N道MATH题”更容易判断示范来源的影响。

这版第三轮主实验使用MATH自身轨迹示范，不默认追加原505条。是否回放原505条是另一个实验因素。600候选及此对照是新建议，不替换用户已经完成的第三轮数量或结果。

## 5. GRPO处理步骤

1. 使用GRPO所属分区的MATH题，保留problem、gold、subject、level和来源ID。gold仅供奖励程序使用。
2. 用最终选定SFT checkpoint每题生成4份回答，固定采样与生成长度。筛选与在线训练采用同一冻结判分逻辑。
3. 保存4份原文，分别记录正确性、格式、EOS和解析状态。解析/截断问题单列诊断，不能通过删掉失败回答来提高k/4。
4. 优先保留1、2、3份正确的题；0/4和4/4留作诊断。四次采样只是粗估，不保证上线训练后仍是混合组。
5. 合格题≤1024时全部保留；超过1024时按subject、level和观测k分层抽样，接近合格池的实际比例。先不强制25/50/25难度配额，不为了满1024复制题目或填入大量GSM8K。
6. 正式GRPO重新生成回答，用答案正确性0/1加辅助格式奖励训练；离线筛选回答不当作SFT标签。记录实际生成题组数、不同题数、屏蔽组数和生成tokens。

最多1024是首轮算力预算，不是预言筛选成功率。允许多轮访问同一个训练问题，但每轮在线重新生成，并如实记录重复；不把题目访问次数称为不同题目数。

执行参数及诊断细节见[GRPO数据方案](GRPO_DATA_PLAN.md)。

## 6. GSM8K什么时候加入

第一版MATH主实验不加入GSM8K。若开发验证显示明显算术、多步文字建模或单位换算短板，再准备少量对应GSM8K train候选，并用同一起点筛选。

先比较纯MATH与90% MATH / 10% GSM8K两种题目采样方案；10%仅是低成本探索起点。固定总题目访问预算、奖励和超参数，报告实际生成tokens及MATH验证表现；受替换影响的MATH题也需记录。不能把GSM8K默认看成对当前模型一定简单，也不为其编造MATH level。

主测试仍是冻结MATH L2–3；如果要声称跨数据集泛化，另加GSM8K test独立报告，不与MATH分数合成一个正确率。没有验证收益时保留更简单的纯MATH配置。
